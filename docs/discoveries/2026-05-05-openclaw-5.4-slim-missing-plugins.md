# OpenClaw 2026.5.3+ removed `brave` and `memory-lancedb` from the bundled image

**Date:** 2026-05-05
**Status:** Confirmed. Working around it by pinning `UPSTREAM_PIN=2026.5.2`. A 5.4 upgrade requires either installing the missing plugins as `@openclaw/*` npm packages in our `Dockerfile` or migrating config to the bundled replacements.

## TL;DR

- The container crash-looped on every attempt to upgrade past `2026.5.2` with **exit code 1, no app logs** (Azure files mount + Cloudflared init succeeded; the `openclaw gateway` process died before its stdout was flushed).
- Captured the real error by spinning up a one-shot ACI debug container (`--restart-policy Never`) with the same image + secrets:
  ```
  Gateway failed to start: Error: Invalid config at /home/node/.openclaw/openclaw.json.
  tools.web.search.provider: web_search provider is not available: brave
    (install or enable plugin "brave", then run openclaw doctor --fix)
  plugins.slots.memory: plugin not found: memory-lancedb
  Run "openclaw doctor --fix" to repair, then retry.
  ```
- Inspecting `/app/dist/extensions/` inside the 5.4 image confirms: **no `brave/`, no `memory-lancedb/`** directories. `openclaw plugins inspect brave` and `... inspect memory-lancedb` both return `Plugin not found`.
- The official docs ([Tools → Plugin](https://docs.openclaw.ai/tools/plugin#core-shipped-with-openclaw)) still list both as "core (shipped with OpenClaw)" — but they are **not in the 5.3+ image at all** (see "`-slim` is not a different image" below).
- 5.2 still ships both as bundled stock plugins (`stock:brave/index.js`, `stock:memory-lancedb/index.js`), which is why `2026.5.2` works without any extra steps.

## `-slim` is not a different image

We pull `ghcr.io/openclaw/openclaw:${tag}-slim`, but it turns out `${tag}` and `${tag}-slim` are **the same image with two tag aliases pointing at the same SHA256 digest**:

```
ghcr.io/openclaw/openclaw:2026.5.4       sha256:7f4dfd4ed0d5469a4f12eccaa5f46b0c70fca802806be625dce782e69203e689
ghcr.io/openclaw/openclaw:2026.5.4-slim  sha256:7f4dfd4ed0d5469a4f12eccaa5f46b0c70fca802806be625dce782e69203e689
ghcr.io/openclaw/openclaw:2026.5.2       sha256:1881e26c41f3139677e8ba9e06be18e6588f486d4b8dbf9efeba84d27a9fad76
ghcr.io/openclaw/openclaw:2026.5.2-slim  sha256:1881e26c41f3139677e8ba9e06be18e6588f486d4b8dbf9efeba84d27a9fad76
```

The OpenClaw Docker docs describe only one base-image dimension: their runtime image is built `FROM node:24-bookworm-slim` (that's Node's `slim` Debian variant, not an OpenClaw "slim" variant). The `-slim` suffix on OpenClaw's own tag is purely cosmetic. **Switching to a non-slim OpenClaw tag would not bring `brave` or `memory-lancedb` back.**

## Repro / how it was diagnosed

The production deployment runs the wrapper image `${ACR_NAME}.azurecr.io/openclaw:custom-${upstream}-${WRAPPER_REV}`, which is `FROM ghcr.io/openclaw/openclaw:${upstream}-slim`. Every 5.3 / 5.4 wrapper rebuild produced an image that crashed in 8–10 seconds inside ACI with empty container logs.

The reason logs were empty: `docker-entrypoint.sh` writes the gateway error to stderr seconds before `openclaw-init.sh`'s trailing `sleep 30` can flush, but ACI's hosted log collector apparently drops anything that exits within ~10s when stdout was never flushed. Workaround: deploy the same image to a **fresh** container group with `--restart-policy Never` and a different name, so the first stderr survives:

```bash
az container create \
  --name openclaw-debug-real --restart-policy Never \
  --image ${ACR_NAME}.azurecr.io/openclaw:custom-2026.5.4-2 \
  --secure-environment-variables OPENCLAW_CONFIG_B64=... [...rest of secrets] \
  ...
sleep 30 && az container logs ...
```

That surfaced the actual error message above. Direct `ls /app/dist/extensions/` and `gosu node openclaw plugins inspect <id>` confirmed both plugins are absent.

## Available alternatives in 5.4

Bundled web-search providers in 5.4 `/app/dist/extensions/`:
`duckduckgo`, `exa`, `firecrawl`, `perplexity`, `searxng`, `tavily`, `web-readability`, plus `google` (Programmable Search) — but **no `brave`**.

Bundled memory plugins:
`memory-core` (default, bundled), `memory-wiki` (bundled, sits beside an active memory plugin), `active-memory` (bundled but disabled by default) — but **no `memory-lancedb`**.

## Decision

**Stay on `2026.5.2` for now.** Reasons:
- We rely on Brave Search (we already have a `BRAVE_SEARCH_API` key; switching to Tavily/Exa would mean a new account + key + billing).
- We rely on the LanceDB-backed long-term memory layer with auto-recall/capture and Azure Files persistence (`az://openclaw-memory/lancedb`). `memory-core` is described as "bundled memory search" — it's not a drop-in for the LanceDB capture/recall pipeline.

To prevent silent regressions, `scripts/env.sh` now pins `UPSTREAM_PIN="2026.5.2"` with a FIXME comment.

## Path forward (deferred)

When we want to upgrade past 5.2:

1. **Install the missing plugins as npm packages in our `Dockerfile`**:
   ```dockerfile
   RUN npm install -g @openclaw/brave-plugin @openclaw/memory-lancedb-plugin
   ```
   (Verify the exact npm package names against [OpenClaw-owned npm packages](https://docs.openclaw.ai/tools/plugin) before committing — package names occasionally shift during the ClawHub migration. If those exact names are gone from npm, search ClawHub: `openclaw plugins search brave`.)

2. **Or accept the migration** and switch `tools.web.search.provider` to one of the bundled search plugins (`tavily` looks like the closest equivalent — same "web search" capability, similar API shape) and `plugins.slots.memory` to `memory-core`.

Either path needs a one-shot debug-container smoke test (the same `--restart-policy Never` recipe above) before we flip `UPSTREAM_PIN` back off.

## Memory plugin layering — does memory-wiki conflict with memory-lancedb / memory-core?

**Short answer: no, they are complementary by design.** Per [memory-wiki docs](https://docs.openclaw.ai/plugins/memory-wiki):

> `memory-wiki` is a bundled plugin that turns durable memory into a compiled knowledge vault. It does **not** replace the active memory plugin. The active memory plugin still owns recall, promotion, indexing, and dreaming. `memory-wiki` sits beside it.

The two layers:

| Layer | Owns | Configured via |
|-------|------|----------------|
| **Active memory** (one of: `memory-core`, `memory-lancedb`, `qmd`, `honcho`, …) | recall, semantic search, auto-capture/auto-recall, dreaming, promotion | `plugins.slots.memory = "<id>"` (exclusive slot — exactly one) |
| **memory-wiki** | compiled knowledge wiki, structured claims with provenance, dashboards, wiki-specific search/get/apply tools | `plugins.entries.memory-wiki` (separate plugin, runs in parallel) |

`plugins.slots.memory` is an **exclusive slot**, so picking `memory-lancedb` automatically force-disables `memory-core` for the active-memory role; only one of those is live at a time. `memory-wiki` is a different concern and is on its own knob.

The docs explicitly recommend the hybrid pattern we already run:

> A strong default for local-first setups is:
> - QMD (or `memory-lancedb`) as the active memory backend for recall and broad semantic search
> - `memory-wiki` in `bridge` mode for durable synthesized knowledge pages

`bridge` mode lets `memory-wiki` read public artifacts the active memory plugin exports (dream reports, daily notes, memory root files, memory event logs) through SDK seams — no private-internal access — and compile them into provenance-rich wiki pages. That matches our current `vaultMode: "bridge"` config exactly.

Practical division of labor in agents:
- `memory_search corpus=all` — one broad recall pass that spans both layers.
- `memory_search` (default) — active layer only (LanceDB).
- `wiki_search` / `wiki_get` — wiki layer only, with claim provenance.

So our current config is correct: `plugins.slots.memory: "memory-lancedb"` for the active recall layer, `memory-wiki` enabled in `bridge` mode for the compiled-knowledge layer. They do not collide.

## What changed in this branch as a result

- `scripts/pull-latest.sh` — added `UPSTREAM_PIN` env override (lets us pin past a regression without manual ACR juggling) and a defensive prerelease/draft filter.
- `scripts/deploy.sh` — always rebuilds against the resolved/pinned upstream before deploying (set `SKIP_BUILD=1` for fast config-only iteration); prevents silent re-deploys of a stale wrapper image.
- `scripts/env.sh` — `UPSTREAM_PIN="2026.5.2"` (pin), `WRAPPER_REV="3"` (bumped because `openclaw-init.sh` changed).
- `docker/openclaw-init.sh` — bake `NODE_COMPILE_CACHE=/var/tmp/openclaw-compile-cache` and `OPENCLAW_NO_RESPAWN=1` (per `openclaw doctor` recommendation; trims Node startup ~1–3s per CLI invocation).
- `config/config.json` — primary back to `google/gemma-4-31b-it`, fallbacks `mistral-nemotron → model-router-1 → mistral-large-3`, Google provider restored without `apiKeyEnv` (that field is rejected by the runtime config validator and was a separate cause of an earlier crash on 5.4).

Verified: container Running on `${ACR_NAME}.azurecr.io/openclaw:custom-2026.5.2-3`, gateway healthy, `gemma-4-31b-it` answering through `openclaw agent` end-to-end.
